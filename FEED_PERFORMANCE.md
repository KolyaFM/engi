# Задержка ответа и перехода: диагностика и исправления

Проблема подтверждена на уровне сервисов. До изменения каталог учебных целей создавал полный пул заданий при каждом ответе. При переходе каталог строился повторно, затем строился ещё один пул для выбора. Компиляция контрактов и вариантов ответа выполнялась синхронно на основном потоке. На большом наборе это способно остановить анимацию и реакцию кнопок.

## Изменения

- Каталог хранится в ограниченном кеше из одной записи. Ключ включает полное содержимое графа и конфигурационные learningState; изменение даже внутри существующего объекта инвалидирует кеш. Память целей FSRS и ежедневный план всегда читаются и рассчитываются заново. Возвращаемое значение копируется, чтобы потребитель не изменил кеш.
- До генерации оставлены только единицы, связанные с потенциально допустимыми целями. Финальные ограничения сроков, раскрытий, бюджета и зачёта остались на прежнем месте. Полный список включённых единиц остаётся доступным для проверки всех участников набора и выбора неверных ответов.
- При подборе повторно используются уже прочитанные памяти каталога.
- Обновление видимости подготовленного задания больше не перечитывает весь граф каждую секунду. Проверка актуальной ревизии при ответе сохранена.
- Предзагрузка изображений использует выбранные задания; больше нет полного чтения графа и поиска по старому расписанию на каждой карточке. Подготовки будущих, ещё не выбранных карточек это пока не добавляет.
- Обновление панели дня не задерживает показ сохранённого результата ответа.
- Подготовка следующего задания идёт одновременно с 180 мс анимации выхода, вместо последовательного ожидания.

## Воспроизводимые измерения

`node --import tsx scripts/check-feed-latency.mjs`

Настоящие сервисы, транзакции fake-indexeddb и FSRS; 16 целей готовы к повторению, остальные назначены после сегодняшнего дня. Формат choice, шесть ответов и переходов на размер. Каталог предварительно прогрет через снимок прогресса. Это измерение пути ответа и перехода, не холодного запуска и не реального браузера. Медианы в миллисекундах:

| Объекты | Ответ до | Ответ после | Переход до | Переход после |
|---|---:|---:|---:|---:|
| 32 | 28.3 | 5.5 | 29.8 | 6.9 |
| 128 | 114.3 | 10.5 | 135.2 | 14.1 |
| 256 | 327.9 | 16.7 | 426.1 | 23.9 |

Исходные измерения: FEED_LATENCY_BEFORE.json и FEED_LATENCY_AFTER.json. До-версия уже содержала диагностический модуль, но не оптимизации. Измерения единичные на разработческом окружении, не обещание тех же чисел на телефоне.

`node --import tsx scripts/check-feed-latency.mjs --fresh`

FEED_LATENCY_FRESH.json проверяет отсутствие памяти всех целей. На 256 объектах первые два перехода занимают 112.4 и 125.8 мс, третий — 25.7 мс после заполнения трёх мест первого обучения. На этапе новых целей пул всё ещё большой. Эти числа относятся к choice; смешанная лента с большим количеством изображений и вариантов требует отдельного измерения. Холодная сборка каталога тоже остаётся дорогой.

## Трассировка браузера

В консоли разработчика:

```js
engiPerformance.start()
```

После нескольких ответов и переходов:

```js
engiPerformance.stop()
console.table(engiPerformance.report())
// При необходимости скопировать результат:
JSON.stringify(engiPerformance.report(), null, 2)
```

Трассировка выключена по умолчанию, сохраняет до 1000 измерений в памяти и не записывает ответы или идентификаторы объектов. start очищает предыдущую запись. Интервалы вложены друг в друга, их нельзя складывать:

| Этап | Что показывает |
|---|---|
| ui.answer.writeQueue | Ожидание записей видимости/взаимодействия перед ответом |
| ui.submit | Обработка ответа до установки результата в состояние React |
| answer.total | Весь сервис ответа, включая ожидание транзакции |
| ui.advance.writeQueue | Ожидание записей перед переходом |
| advance.total | Весь сервис перехода |
| bundle.read | Чтение графа для перехода |
| selection | План и выбор следующего задания |
| catalog | Получение каталога, включая проверку ключа кеша |
| candidates | Генерация пула и компиляция контрактов |
| task.prepare | Подготовка выбранного контракта и попытки |
| ui.cardLoad | Загрузка обратной связи и готовность выбранного изображения перед показом карточки; не измерение фактической отрисовки GPU |
| browser.longtask | Блокировки основного потока дольше 50 мс, если браузер поддерживает Long Tasks API |

Большой candidates укажет на генератор. Большой bundle.read — на чтение данных. Большое ожидание writeQueue при коротких вычислениях — на накопление записей/транзакций. Большой cardLoad — на загрузку обратной связи или изображений. Для точной привязки к кадрам и декодированию изображения следует записать браузерный Performance trace: обработка клика, main-thread tasks, React commit, paint и загрузка изображения. Этот стенд визуальный профиль не заменяет.

## Проверка корректности и следующие шаги

217/217 тестов прошли, production build прошёл. Новые проверки: инвалидирование кеша изменением содержимого и suspension, защита кеша от изменения потребителем, сохранение полного состава set при предварительном отборе, отсутствие побочного влияния трассировки. После изменения повторены четыре сценария по 90 виртуальных дней: REAL_FEED_LATENCY_90_DAYS.json. Ограничения FSRS, раскрытий и ежедневного бюджета проверяет тот же настоящий сервисный стенд.

Реальный Chromium/телефон и отображение кадров здесь не проверены. Ускорение сервисов подтверждено; мгновенность всего интерфейса не объявляется достигнутой.

Следующий шаг — пул лёгких описаний кандидатов с построением вариантов и контракта только выбранного задания. Нужно отдельно проверить равенство доступных целей, разнообразие, ошибки материализации, изменения графа и отсутствие голодания. Затем безопасная фоновая подготовка следующей карточки с повторной проверкой расписания и раскрытий перед показом. Заранее показывать или засчитывать эту карточку нельзя.
