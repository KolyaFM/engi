# Целевая архитектура и реализация Энги 3.0

## Общий граф

`entities` хранит самостоятельные объекты с постоянным внутренним ID, типом, именем, алиасами, внешними идентификаторами и описанием. Имена не уникальны. `entityTypes` — общий справочник типов с алиасами.

`propertyDefinitions` содержит типы значений, ограничения на типы объектов/ответов, множественность, настройку обучения и шаблоны вопросов. Свойства сопоставляются по названию и алиасам; несовместимое определение отклоняется с объяснением.

`facts` — отдельные утверждения «сущность → свойство → значение». Ссылки на сущности образуют граф. Обратные списки вычисляются по `valueEntityId`; дублирующие связи «написал» не создаются. В каждом факте сохраняются основной источник, массив источников, проверка, возможность обучения, точность даты и при необходимости единица измерения числа.

Даты хранят диапазон и точность (`year`, `month`, `day`, `circa`, `range`). Более точная дата не заменяет старую молча: импорт предлагает разрешить расхождение. Нормализация текстовых значений применяется только при сравнении; отображаемая запись сохраняется.

`media` привязывает файл к объекту с ролью, лицензией, источником, основным изображением и пригодностью для узнавания. Файлы в Cache Storage адресуются SHA-256, записи — в IndexedDB. `tags` / `entityTags` служат для поиска и тематических меток.

## Колоды

`decks` / `deckMembers` хранят независимые подборки. Колода задаёт изучаемые свойства, узнавание по изображениям и исключения фактов. Пустой список свойств означает «не учить свойства»; отсутствующий список — «все доступные свойства». Связанные справочные объекты не попадают в состав колоды автоматически.

Родитель колоды служит для навигации. Состав остаётся явным и не наследуется динамически. При миграции старого тега-колоды родитель получает снимок объектов всех дочерних тегов, чтобы сохранить старый состав.

`Неразобранное` — виртуальная подборка объектов вне активных колод. Удаление колоды или участника не удаляет знания и прогресс.

## Импорт

`schema-v3.ts` строго проверяет декларативный формат. `semantic-merge.ts` строит план на копии базы; файлы, колода и прогресс до подтверждения не меняются. Внутренние новые ID стабильны в пределах предварительного просмотра, включая изменение решений.

Сопоставление использует тип, нормализованное имя / алиасы, уточняющие факты и внешние идентификаторы. Неоднозначности, архивные совпадения и противоречия требуют выбора. Единственное имя без противоречащих известных сведений принимается как совпадение; неполнота знаний не позволяет доказать реальную идентичность, поэтому для одноимённых объектов нужны уточнения. Семантическая LLM и нечёткое автоматическое слияние не используются.

Сначала сопоставляются все объявления сущностей, затем ссылки и факты. Книга может ссылаться на автора, описанного ниже. Ссылки по именам в пределах пакета также проверяются на неоднозначность.

Повторный факт объединяет источники и сохраняет свой ID. Замена однозначного ответа архивирует старый факт и добавляет новый: история старого знания остаётся, новое получает новую память. «Спорный» исключает оба значения из обучения. Отсутствие записи в новом пакете не означает удаление.

`declarative-pack.ts` проверяет ZIP, изображения и хеши, сохраняет файлы, затем метаданные одной транзакцией. Перед коммитом проверяется, что граф не изменился после просмотра. Отмена или ошибка до коммита не оставляет частичную колоду; новые неиспользуемые файлы убираются при ошибке. Предварительный просмотр и выбор доступны в `ImportPreview`.

Повторный пакет узнаётся по внутреннему хешу его разобранного содержимого и файлов. Поэтому переименованная колода при точном повторном импорте находится по сохранённому соответствию. У нового содержимого и одинакового названия пользователь выбирает существующую колоду или отдельную; настройки существующей колоды сохраняются.

## Обучение

ID единицы памяти: `ku:entity:<id>:visual_identity` либо `ku:fact:<id>:forward/reverse`. Форматы и разные изображения одного знания используют общую память. Разные факты и направления независимы; колоды пользуются общей памятью.

`learningState` хранит FSRS и состояние освоения. `reviewEvents` хранит попытки и снимок проверяемого ответа, поэтому правка знания не переписывает прошлую историю. Состояние и событие ответа сохраняются атомарно; повторная отправка того же задания идемпотентна.

Для многозначного поля приложение не задаёт вопрос с единственным произвольным ответом. Если полный набор значений явно отмечен (`completeProperties` при импорте, флаг в редакторе), создаётся множественный выбор. Результат относится отдельно к каждому участвующему факту; лишний вариант не даёт положительного доказательства. При случайном повторении ещё не наступившего знания его FSRS не пересчитывается. Приостановленные единицы не обновляются.

Если набор не помечен полным, несколько значений отображаются в графе, но неоднозначный вопрос не генерируется. Полные многозначные задания сейчас поддержаны для ссылок на сущности. Для текстовых / числовых наборов это ограничение первой версии.

## Объединение дублей

`entity-merge.ts` переносит входящие ссылки, собственные факты, изображения, теги и колоды. Совпадающие факты объединяются, конфликтующие одиночные значения становятся спорными. Старый объект архивируется, соответствия единиц сохраняются в `targetMappings`; исторические события не переписываются.

Память одинаковых знаний объединяется консервативно: минимум стабильности, ранний срок повторения, максимум сложности; успешные попытки не суммируются. Полноценного интерфейса отмены объединения нет; для обратного восстановления нужна предварительная копия.

## Хранение и миграция

Схема IndexedDB v4 добавляет `decks` и `deckMembers`. ID сущностей / фактов и память не пересоздаются. Старые теги сохраняются; на их основе создаются отдельные колоды, активные старые сессии завершаются.

Резервная копия v3 содержит весь граф, все доступные файлы, колоды, память, историю, настройки и соответствия старых целей. Восстановление переносит сохранённые внутренние ID; это перенос / восстановление базы, а не семантическое объединение двух независимых резервных копий. При совпавших конфликтующих ID нужно восстановить копию в пустую базу.

Приложение остаётся локальным. Облачная синхронизация, автоматический откат после закрытия браузера в момент записи, восстановление из физически повреждённого Cache Storage и автоматическое определение тождественности без достаточных сведений не реализованы.
