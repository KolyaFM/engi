# Выбор из описаний, сборка только выбранного задания

Продолжение STUDY_CORE_GROUPS.md. Основной путь смешанной ленты перестал создавать ответы и контракты для всего пула на каждом переходе.

## Устройство

1. При новой конфигурации существующий генератор один раз проверяет доступные одиночные варианты. Его проверенный результат преобразуется в описания: рецепт, объекты и определения целей. UUID карточек, неверные варианты ответа и TaskContract не сохраняются в пуле.
2. Кешируются не более двух конфигураций/областей. Ключ включает содержимое графа, конфигурационные learningState, область и формат. Изменение имён, алиасов, фактов, изображений, настроек или suspension требует новой проверки. Кеш хранится только в памяти процесса; после перезагрузки строится снова. При вытеснении записи она тоже строится снова.
3. При каждом выборе заново читаются память целей, ежедневный план, сроки FSRS и раскрытия. Из описаний исключаются недопустимые цели. Ничего из этих динамических данных не кешируется.
4. Из доступных описаний строятся ограниченные групповые варианты. Для них проверяются состав, различимость подсказок, ответы и размер; компиляция контрактов всех групп больше не нужна.
5. Прежний селектор выбирает цель/формат по срочности, ошибкам, закреплению, ожиданию и разнообразию объектов/взаимодействий.
6. Только выбранный вариант превращается в настоящее задание. Для одиночного вопроса заново выбираются подсказка, изображение и неверные ответы с учётом текущей конфигурации и истории. Для группы собирается выбранное сопоставление. Компилятор проверяет, что получились именно предложенные цели.
7. После успешной сборки сохраняется состояние селектора. Прежний prepareStudyTask сохраняет настоящий контракт и открывает попытку. Успешная компиляция в материализаторе не заменяет эту операцию.

Если вариант не удаётся собрать, он исключается из текущего выбора, а селектор повторно запускается от прежнего состояния. Неуспешная сборка не старит историю, не засчитывает ответ и не расходует бюджет новых целей. Ошибки сохранения базы по-прежнему откатывают общую транзакцию.

Текстовая и графическая подсказки одной цели не фиксируются случайным первым образцом из кеша. В одиночной карточке их выбор остаётся динамическим. Групповое предложение сохраняет свой конкретный тип подсказки, чтобы условия сопоставления не поменялись после выбора.

## Что осталось прежним

Recognition и recall имеют разные памяти; набор ответов имеет одну агрегатную цель. Группы оцениваются по каждой связи. Видимость, раскрытия, повторная отправка ответа, независимый зачёт и лимит первого обучения используют прежние правила.

Timeline, sort и missing продолжают работать через прежний диагностический путь. pickGoalFeedEager сохранён для этого пути и сравнений. goalCandidates остаётся генератором для первичной проверки; его замена при холодном старте здесь не объявляется завершённой.

## Дополнительная корректировка

У complete-set неверные варианты раньше исключались по точному совпадению строк алиасов, а последующая проверка сравнивала нормализованные строки. Поэтому регистр и пунктуация могли случайно сделать сгенерированный набор недопустимым. Отбор теперь сразу нормализует алиасы и убирает повторяющиеся видимые подписи до случайного выбора. Это предотвращает случайную потерю доступного набора при первичной проверке кеша.

## Замеры

Воспроизводимый сервисный стенд:

```sh
node --import tsx scripts/check-feed-latency.mjs --mixed --fresh
node --import tsx scripts/check-feed-latency.mjs --mixed
```

На полностью новой базе, после первоначальной подготовки:

| Объекты | Первые переходы до изменения | Первые переходы после |
|---|---:|---:|
| 32 | 51 / 28 мс | 10 / 10 мс |
| 128 | 136 / 128 мс | 14 / 16 мс |
| 256 | 419 / 407 мс | 33 / 20 мс |

Прежние данные: FEED_LATENCY_GROUPS_FRESH.json. Новые данные: FEED_LATENCY_LAZY_FRESH.json. Третий переход в новом сценарии 256 объектов занял 35 мс. При небольшой готовой очереди и множестве будущих повторений шесть переходов на 256 объектах заняли 19–29 мс: FEED_LATENCY_LAZY.json.

Первые запуски не скрыты: на 256 объектах начальное чтение/подготовка снимка заняло около 384–400 мс, последующий старт смешанной сессии с первой проверкой пула — 389–407 мс. Эти операции последовательны в стенде. Перестроение после изменения данных или вытеснения кеша тоже может задержать переход. Ускорен обычный путь ответов и переходов при стабильной конфигурации; холодная подготовка ещё требует оптимизации.

Это отдельные прогоны в разработческом окружении с настоящими сервисами и fake-indexeddb, без отрисовки браузера и загрузки реальных изображений. Измерения не являются гарантией тех же чисел на телефоне. Трассировка браузера из FEED_PERFORMANCE.md дополнена этапами `proposals`, `groups`, `materialize`: получение описаний, создание групповых описаний, сборка выбранного задания.

## Проверки

234/234 тестов прошли; итоговые TypeScript и production build проверены. Добавлены проверки:

- Равенство множества пар «цели + формат» с полным генератором для смешанного и отдельных форматов, общей области и категории, обычных связей и полных наборов.
- Успешная материализация каждого предложения с теми же целями.
- Инвалидирование кеша после изменения графа, suspension и области; равные значения новых экземпляров графа используют тот же кеш.
- Кеш не замораживает переданный граф и не хранит готовые контракты/варианты ответа.
- Новые UUID настоящих карточек, повторная проверка участников и отсутствие открытия попыток до выбора.
- Сохранение разнообразия image/name в одиночных карточках на фиксированном случайном потоке.
- Отбор неверных вариантов complete-set с нормализованными алиасами.
- Неудачная сборка первого кандидата с успешным повторным выбором; отказ всех кандидатов без изменения счётчиков селектора и прогресса.

REAL_FEED_LAZY_90_DAYS.json содержит четыре прогона настоящей ленты по 90 виртуальных дней: картины, люди с датами, полные наборы и небольшая база. Проверены сроки зачёта, подсказки, исправления, пропуски и предел трёх целей первого обучения. Все исходные учебные цели этих синтетических наборов получили проверки; максимальное количество целей первого обучения осталось 3. Стенд теперь выбирает настоящие групповые задания через ленивый путь.

Изменение количества ответов относительно предыдущей версии не считается доказательством большей эффективности обучения: сократилось потребление случайных чисел генератором, изменились последовательности, а ответы моделируются условным правилом. Проверяются структурные свойства алгоритма. Визуальные и интерактивные проверки Chromium по-прежнему не выполнены.
