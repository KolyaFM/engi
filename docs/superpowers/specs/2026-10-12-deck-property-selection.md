# Выбор свойств колоды: архитектура и производительность

Статус: проект решения для обсуждения; функциональность ещё не внедрена.

## Требуемое поведение

У каждой колоды есть меню «Что изучать». Оно содержит доступные свойства участников колоды и отдельный пункт распознавания объекта по основному изображению. Названия берутся из определений свойств, а не из тегов или заранее заданного списка. Флаг как отдельный факт не объединяется с основным изображением карты.

Отключение скрывает соответствующие обязательства из этой области обучения, но не удаляет память, ошибки, историю, знакомство или расписание FSRS. Включение ранее пропущенного свойства создаёт знакомство только с ещё не представленными свойствами объекта. Возвращение изучавшегося свойства сохраняет прежний прогресс. «Знаю» остаётся исключением из автоматического повторения.

Если один объект входит в несколько выбранных колод, область обучения — объединение разрешённых знаний: достаточно включения в одной колоде. Одно знание считается один раз. На плитке каждой колоды используются её собственные настройки; в общей панели — объединение выбранных колод.

## Что есть сейчас и где риск

- `Deck.learning` уже содержит настройки автора пакета: `propertyIds`, `imageRecognition`, `excludedFactIds`. Это не место для личного выбора: обновление пакета не должно перезаписывать предпочтения пользователя.
- `createDeckTargetIndex` получает цели через `compositionContext`, рецепты и их пулы. Первичная стоимость зависит от количества форматов и областей генерации, хотя списку настроек они не нужны.
- `deckStudyScope` повторно создаёт индекс и объединяет цели; его вызывают подбор, счётчики и операции сессии.
- Кэши `compositionContext` и `canonicalTargets` используют сериализацию содержимого. Изменение временной области может создавать новый ключ и повторно строить рецепты.
- `deckOverview` для каждой колоды заново строит карту памяти и фильтрует каталог. Есть поиск `active.find` внутри цикла по памяти целей.
- `getBundle` заново читает все таблицы содержимого. Это не должно происходить при открытии меню или переключении свойства.
- `compileIntroContract` для первого знакомства учитывает все проверенные факты объекта. После введения выборочных свойств это не гарантирует соответствие реально показанным данным.
- Квитанция `introReceipt` использует сессию и объект. Повторное знакомство с другими свойствами того же объекта может ошибочно считаться дублем.

Это места для измерений и изменений, а не утверждение, что каждое из них уже вызывает наблюдаемые задержки.

## Три независимых слоя

### 1. Содержимое и структурный каталог

`DeckStudyCatalog` — неизменяемый индекс для одной версии содержимого базы. Общие индексы: объект по ID, свойство по ID, факты и допустимые изображения по объекту, колоды по объекту, цели по знанию, знания по объекту. Индекс колоды содержит:

- доступные свойства: ID, название, тип, число участников с допустимым знанием;
- распознавание основного изображения как отдельную возможность;
- наборы канонических знаний и целей по свойству;
- исходный выбор из настроек пакета.

Каталог строится из участников колоды и допустимых знаний. Он не генерирует задания, варианты ответа или все комбинации форматов. Используется общая проверка допустимости, согласованная с генератором: архивность, проверенность, `learnable`, ограничения типов, наличие медиа, полнота многозначных фактов. Не создавать вторую независимо развивающуюся систему правил допустимости.

Название свойства — отображение; идентичность — стабильный внутренний ID. Теги могут изменять группировку и подбор похожих объектов, но не идентичность личной настройки.

Первое внедрение допускает адаптер к существующему каноническому каталогу, если он уже загружен. Меню не должно самостоятельно запускать `recipes` / `eligible`. Общий индекс должен покрывать все допустимые свойства, а не только те, что включены автором по умолчанию.

### 2. Личные настройки

Отдельная запись `appMeta`: версия схемы, номер изменения, настройки по ID колоды. Для изменённой пользователем колоды хранить исключённые ID свойств и выключенное распознавание; отсутствие записи означает наследование исходного выбора пакета.

При первом сохранении меню исходный выбор преобразуется в список исключений среди текущих доступных свойств. После этого новые допустимые свойства автоматически включаются; исключения по стабильным ID сохраняются. Для колоды без личной настройки действуют исходные настройки автора. Явное `learnable:false`, неподтверждённые данные и исключённые факты не обходятся пользовательским переключателем.

Все настройки выключены — допустимое состояние. Колода остаётся выбранной, но не добавляет обязательств. Если общая область пуста, кнопка старта недоступна с коротким объяснением. Обновление пакета и резервная копия сохраняют личные настройки. Исчезнувший ID не участвует в обучении; его исключение не следует молча терять при временном отсутствии содержимого.

### 3. Область обучения

`StudyScope` — производная проекция структурного каталога, выбранных колод и личных настроек. Содержит наборы активных знаний, целей, targets и объектов. Не меняет граф, память и настройки автора.

Одну проекцию передавать в знакомства, подбор одиночных и групповых заданий, повторения, ошибки и счётчики. Память хранится глобально. Отключение — фильтрация области, а не изменение `suspended` или FSRS.

Учитывать свойства первичных и вспомогательных целей группового задания. Отключённое знание нельзя незаметно возвращать как сортируемый объект, опорную дату или правильный ответ. Контекстные неверные варианты допустимы, если они не спрашивают и не раскрывают отключённое свойство. Фактический показ имени или изображения фиксируется существующим механизмом раскрытий независимо от настроек расписания.

## Работа с прогрессом

Отдельная проекция прогресса создаёт карты состояния по каноническому знанию и по цели один раз на изменение прогресса. Для колод предвычисляется агрегат по каждому свойству: всего, освоено, в обучении, к повторению, ошибки.

Выбор свойств суммирует готовые агрегаты одной колоды. Общая панель объединяет ключи знаний, а не складывает цифры колод: иначе пересекающиеся колоды дадут двойной счёт.

Количество считается в знаниях свойств, не в объектах, форматах или числе изображений. Разные навыки одного свойства объединяются согласно существующему `acquisitionKey`; нельзя заменять его самодельным ключом «объект + название» и потерять множественные значения или ревизии.

Изменение процентов при отключении свойства ожидаемо: знаменатель — выбранные знания. Глобальный экран статистики хранит общую историю независимо от текущего выбора.

## Знакомство с вновь включёнными свойствами

Дельта вычисляется как активные допустимые targets объекта минус targets с существующим знакомством/памятью. Не создавать очередь из всех объектов при переключении: индекс позволяет выбирать следующее подходящее знакомство при обычном подборе.

Знакомство имеет отдельный устойчивый `introId`, который сохраняется при перезагрузке. Квитанция и контракт привязаны к этому эпизоду, а не только к объекту. Повторная отправка эпизода идемпотентна; новое знакомство того же объекта — новый эпизод. Для старых сессий сохранить совместимый путь чтения и назначение ID.

`ObjectIntroCard` и `compileIntroContract` используют один список реально представленных targets / claims. Первый показ не означает раскрытие всех отключённых фактов. Дополнительное свойство не расходует дневной лимит новых объектов повторно. До завершения знакомства оно не попадает в обычное обучение. После завершения действует существующий lifecycle.

Если карточка уже была знакома или объявлена «Знаю», повторное включение не сбрасывает её состояние. Изменённое значение факта обрабатывается существующей системой ревизий, отдельно от переключения настроек.

## Кэш и правила обновления

Не создавать кэш под каждый формат × тег × набор галочек. Достаточно структурного каталога, проекции прогресса и ограниченного кэша текущих областей. Хранить версии каталога явно; алгоритм построения тоже имеет версию.

| Событие | Обновляется | Не перестраивается |
| --- | --- | --- |
| Открытие меню | Локальное состояние открытого меню | Содержимое, каталог, цели, задания |
| Галочка в меню | Локальный выбор и агрегаты колоды | Все факты, рецепты, FSRS |
| Сохранение выбора | Одна запись настроек, область обучения | Структурный каталог, память |
| Ответ на задание | Память затронутых знаний, проекция прогресса | Список свойств, содержимое |
| Наступление срока повторения | Статусы сроков и счётчики | Структурный каталог |
| Импорт/изменение содержимого | Каталог новой версии, область | Неизменённая история памяти |
| Изменение выбранных колод | Объединение готовых наборов | Каталоги отдельных колод |

Открытое меню использует черновик и одну кнопку «Готово»: галочки отвечают сразу, база записывается один раз. Не вызывать общий `reload()` после каждой галочки. Сохранение атомарно; при ошибке черновик остаётся и доступен повтор сохранения. Номер изменения защищает от старого асинхронного результата.

На первом этапе каталог переиспользуется по неизменяемому snapshot, общий индекс передаётся в операции явно. При смене snapshot содержимого индекс пересоздаётся один раз. Не оставлять его только в React: сервис обучения должен пользоваться тем же провайдером.

Если трассировка подтвердит, что полные чтения/сериализация доминируют, следующий шаг — единый провайдер содержимого с транзакционным `contentRevision` и объединением параллельных загрузок одной версии. Все записи содержимого, импорт, восстановление, слияние, удаление и миграции обязаны обновлять ревизию в той же транзакции; разные базы и вкладки не делят один безымянный глобальный кэш. До покрытия всех путей записи существующее обнаружение изменений не удалять. Содержимое и личные настройки имеют разные ревизии.

Не выносить небольшую фильтрацию в worker заранее: копирование графа и синхронизация могут стоить больше. Worker рассматривается для измеренного дорогого построения больших каталогов, а не для каждого клика.

## Изменение настроек и сохранённая сессия

Сессия хранит ID выбранных колод и ревизию области. При старте/возобновлении сравнивается ревизия. Сохранённый вопрос, знакомство и очереди валидируются по новой области до показа. Отключённая карточка пропускается без записи ошибки или ответа; допустимое выполненное задание сохраняет свой результат.

Если настройка изменилась в другой вкладке во время открытого вопроса, не менять карточку посреди жеста. Синхронизировать на безопасной границе; перед сохранением ответа проверять его допустимость и не засчитывать исключённое знание. Если сессия утратила все цели, вернуть на экран колод с коротким сообщением.

## Проверки перед внедрением

1. Произвольные типы, названия и теги; разные свойства у участников; изображения как факты и основное распознавание.
2. Две колоды с общим объектом: включение в одной, выключение в другой, ни двойного прогресса, ни двойных ошибок.
3. Выключение в обучении, на повторении, с ошибкой, после «Знаю»; состояние FSRS и история побитово сохраняются.
4. Включение пропущенного свойства: только новые поля, без повторного расхода дневного лимита; две новые партии свойств того же объекта в одной сессии.
5. Двойное нажатие «Готово», перезагрузка, ошибка записи, восстановление резервной копии, изменение пакета, старая сессия, другая вкладка.
6. Все форматы используют область, включая опоры хронологии, сортировку, сопоставление, самооценку и раскрытия.
7. Счётчики и процент совпадают с независимым эталонным расчётом на случайных пересекающихся колодах.
8. Трассировка `catalog.build`, `catalog.hit`, `scope.project`, `progress.project`, `settings.write`: при повторном открытии и переключении галочек — ноль полных построений каталога, чтений всего bundle и генераций вопросов.
9. Браузерный профиль с CPU ×4: пакет 50 штатов, несколько пересекающихся колод и синтетический набор тысяч объектов. Цель для отклика галочки — следующий кадр; отдельно измерить холодный старт и тёплый старт. Числа времени — критерии измерения, не обещание результата.

## Границы внедрения

Сначала внедрить настройки, общий каталог/область, согласованные счётчики и корректные знакомства с регрессионными тестами. Затем измерить реальные переходы и только по трассировке расширять общий кэш содержимого. Не переписывать планировщик памяти и формат пакета ради этой возможности. Не переносить личный выбор в `Deck.learning` и не создавать отдельную систему памяти для колоды.
