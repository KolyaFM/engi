# Общий выбор заданий и ритм ленты

Статус: проект после аудита действующего main; продуктовый код ещё не изменён.

## Цель

Разнообразная бесшовная лента, которая проверяет нужные пользователю знания,
сохраняет интервалы памяти и не повторяет успешно отвеченное только ради смены
оформления. Все существующие механики имеют явный путь к выбору. Их наличие
не означает обязанность показать каждую в любом коротком занятии.

Запрос пользователя: восстановить умный подбор с весами, избежать частого
«вспомни», проверить реальное поведение тестами и не потерять виды заданий.
Параметры частот ниже — предложение для проверки, а не научная норма.

## Подтверждённые проблемы

- На main `0c2f77f` повторён прогон настоящего trainer service с IndexedDB,
  показами ответов, правильными ответами, возобновлением занятия и виртуальными
  часами. Шесть стартов: четыре объекта, только портреты либо портреты и годы;
  seeds 1, 17, 41. На 60 заданиях каждого старта доля recall составляет 48–50%.
- В отдельной практике на 3/4/6/12 объектах mixed даёт 12 recall на 24 задания.
  Выбор только choice даёт ноль recall, как и должен.
- Предыдущая правка поставила частоту формата конкретного знания выше общего
  разнообразия. Она выравнивает choice/recall без учёта их разных ролей.
- В lifecycle-feed-service учебный recall, self-check, периоды и хронология
  возвращаются из отдельных веток до общего ранжирования. Порядок условий
  становится скрытым приоритетом. Проверка допуска часто означает немедленный показ.
- Обычные группы собираются из selected (готовой учебной работы). В fallback
  practice перебираются атомарные practicePool; отдельного вызова groupProposals
  для них нет. Одиночный рецепт match не равен групповому сопоставлению.
- goalCandidates mixed включает choice, multi_choice, recall, match, categorize.
  sort/timeline/missing обслуживаются другими путями. Простая замена sort()
  в конце функции не объединит все механики.
- materializeGoalProposal может изменить текст/изображения в вариантах. Нельзя
  учитывать разновидность по предложению, а показывать другую без перепроверки.
- Тесты отсутствия повтора знания проходят даже при 50% recall. Нужны отдельные
  проверки полезности, покрытия и ритма, включая условную доступность форматов.
- Богатая колода ведёт себя иначе: повторный прогон feed-variety дал 5/25 recall
  в свежей ленте, 19/111 за три дня и 18/116 в длинной сессии (20%, 17%, 16%).
  На длинной сессии были 3 настоящих сопоставления, 9 конвейеров и 8 порядков.
  Поэтому нельзя описывать баг как «любая лента всегда наполовину recall»:
  провал особенно заметен на малом наборе и в fallback practice.

Повторно выполнено 47 существующих тестов: 14 по свежим четырём объектам,
частоте recall и разновидностям; 33 по богатой ленте, группам, непрерывности,
периодам и пассивности трассировки. Все прошли. Это исходный аудит, не проверка
предлагаемой политики. Логи: artifacts/feed-design-baseline.log и
artifacts/feed-mechanics-baseline.log; отчёты JSON создаются соответствующими
тестами. Открытые пользовательские занятия не изменялись.

## Подходы

1. Подкрутить штраф recall в нынешнем конце сортировки. Дёшево, но ранние ветки
   и отсутствие групп в practice сохранятся. Не решает поставленную задачу.
2. Сохранить правила памяти и генераторы, объединить представления в одном
   компоновщике с явными этапами выбора. Рекомендуемый подход: меняется подбор,
   не схема хранения, импорт, FSRS или способы оценки ответа.
3. Обучаемый рекомендатель по пользовательским данным. Сейчас нет проверенной
   целевой метрики и данных для настройки. Сложнее объяснять и воспроизводить.

Далее описан вариант 2 как предложение автора; внедрение отдельно от этого аудита.

## Полный перечень

| Семейство взаимодействия | Разновидности, которые нельзя потерять | Допуск и результат |
| --- | --- | --- |
| Выбор одного ответа | объект → свойство; свойство → объект; изображение → имя; имя → основное изображение; изображения-свойства; текстовые ответы; близкие и контекстные числа; проверка путаницы | Однозначные варианты, действующая область обучения. Зачёт по контракту |
| Выбор нескольких | полный набор связей/значений (`multi_choice`) | Самостоятельное составное знание, не N независимых успехов |
| Вспомни | cue текстом/изображением; допустимое прямое/обратное направление | Самоотчёт, специальная учебная репетиция и практика различаются назначением |
| Сопоставление | изображения/текст, свойства и связи | Не менее 3 объектов; совместимая сущность/сигнатура; последняя выведенная пара не становится независимым ответом |
| Категоризация | несколько категорий; две категории как конвейер | Конвейер 3–6 объектов; обе стороны представлены, без фиксированной квоты |
| Порядок | годы, числа, ordering-only; изображения или названия | 3–5 различимых позиций; отношения порядка не доказывают точные значения |
| До/после | конвейер относительно границы года | 3–6 объектов; контекстное доказательство, не знание точного года |
| Периоды на общей шкале | разные типы объектов и разные поля периодов; распознавание выбранной полосы | 3–5 различимых диапазонов, проверка близости/читаемости шкалы, подписи из метаданных поля |
| Граница периода | начало/конец | Отдельная частичная проверка; не закрывает знание всего диапазона |
| Переворачиваемая сетка | self_check, 3–4 совместимых объекта | Самопроверка без оценки памяти; раскрытия только перевёрнутых объектов |
| Legacy timeline/missing | явный режим и старые пакеты | Явно учесть совместимость; не возвращать отвергнутый пользователем ползунок в mixed ради «покрытия» |
| Знакомство | новый объект; новые включённые свойства уже знакомого объекта | Допуск по нагрузке, не проверка памяти |
| Исправление | свежая проверка открытой ошибки | Назначение поверх поддерживаемого формата, а не новый формат |

Все литералы Format должны попадать в реестр совместимости. Новое значение
без политики должно ломать проверку типов/тест реестра. Конвейер, interval и
self-check различаются до fallback к recipe.format; одиночный match/categorize
учитывается как choice. Числовая точность и направление — оси разновидностей,
а не независимые голоса за одно и то же знание.

## Этап 1: доступная работа

Один снимок состояния на выбор: каталог, включённые колоды/свойства, ledger,
память, ошибки, показы и история. Сохраняются существующие правила:

- Будущий срок FSRS/подтверждения не становится наступившим ради разнообразия.
- «Знаю»/suspended и выключенное содержание не превращаются в целевые знания.
- Первые проверки, наступившие подтверждения, FSRS, исправления, знакомства и
  свободная практика остаются разными назначениями.
- Сейчас полезная работа получает преимущество перед развлечением на знакомом.
  Введение следующего объекта не ждёт очередного recall старого, если нагрузка
  позволяет знакомство. Когда новых нет, fallback не обязан закончить ленту.
- Возраст очереди защищает первые проверки и ошибки от вечного вытеснения.
  Разнообразие не переносит просроченное бесконечно.
- Зачёт определяет контракт попытки, не оценка привлекательности кандидата.

Поначалу оставить существующие shouldIntroduce, chooseWorkLane и правила
исправлений как владельцев срочности. Не менять одновременно память и ритм.
Выбор категории работы трассируется отдельно от выбора её представления.

## Этап 2: кандидаты представлений

Общий реестр адаптеров над существующими генераторами. Каждый получает один
снимок и допустимые цели/опоры, возвращает ограниченные предложения или причину
недоступности. Прямой return задания из адаптера запрещён: он не выбирает победителя.

Предложение содержит семейство, подтип, назначение, canonical knowledge keys,
проверяемые цели, опоры, ожидаемые раскрытия, оценку количества действий и
детерминированный ключ. Формирование одного тяжёлого Task отложено до выбора.
Для генераторов, которым пока нужен готовый Task, допускается ограниченный
адаптер; ранний return в общей функции всё равно удаляется.

Группы строятся и для practice из доступного уже показанного содержания, с
practice-контрактом. Это не разрешает подмешивать невыбранные колоды, незнакомые
факты или хорошо известные опоры без нужды. Учебная группа в первую очередь
содержит нужные знания; допускается не более одной явно учтённой опоры, когда
её разрешает существующий компоновщик. Для частичных упражнений сохраняется
общий бюджет раскрытия между точными проверками.

Сопоставление использует жёсткую совместимость типов, затем теги/принадлежность
колоде/историю пар как мягкое сходство. Для хронологии и периодов смешение типов
допустимо; требуются сравнимая величина/единица и корректная подпись поля.

## Этап 3: выбор с весами без перекосов количества кандидатов

Сначала сгруппировать предложения по взаимодействию. 1000 атомарных choice не
должны получать больше шансов, чем одна валидная группа, только из-за количества
строк. Вес принадлежит семейству; внутри него выбираются нужные знания.

Стартовое распределение mixed для моделирования: быстрые объективные задания
45, группы 25, отношения/периоды 15, recall 10, self-check 5. Это веса групп
семейств, не отдельная квота каждого вида. Недоступная механика не создаёт долг.
Внутри группы разные подходящие взаимодействия получают собственную мягкую
защиту от вытеснения; split одного формата на 20 алиасов не увеличивает его вес.

Опциональный recall в mixed дополнительно имеет ограничение: после него минимум
4 других задания; в любом окне 20 завершённых заданий не более 4 recall. В
обычном богатом наборе целевая доля около 10–15%, допустимый верх 20%. Self-check
не служит обходом ограничения: его доля и длительность считаются отдельно.
Окно считается по завершённым заданиям, не по интро/ответам внутри группы.

Исключения явные: пользователь выбрал recall-only; нет ни одной валидной
альтернативы и нет допуска к новому; конкретная проверка необходима по контракту
исправления/навыка. В fallback повышать долю можно только с записанной причиной.
До fallback пробовать объективное представление того же знания; отсутствие
вариантов нельзя превращать в неверное/неоднозначное задание. Исправления
учитываются в фактической статистике recall, хотя могут нарушать мягкий ритм.

Предлагаемый механизм весов: нормировать веса только среди сейчас допустимых
семейств; по ограниченной истории вычислять ожидаемое и фактическое обслуживание.
Ограниченный бонус недополучившего семейства, штраф недавнего формата и умеренный
бонус нужных целей составляют оценку. История одной canonical цели выбирает
разновидность внутри семейства и НЕ стремится выровнять число recall/choice.
Окончательные коэффициенты выбрать сравнением нескольких конфигураций в модели;
не записывать непроверенную «волшебную формулу» как готовое решение.

При близких оценках — seeded tie-break, воспроизводимый по session/turn/revision.
Не взвешенная лотерея без контроля: она допускает случайные длинные серии.
Бонус ожидания формата ограничен и никогда не отменяет правила памяти.
Обновлять обслуживание только после принятого фактического показа/завершения,
не за подготовленные/невалидные предложения. Reload не расходует квоту дважды.

Внутри выбранного семейства: нужность и возраст работы, затем давность canonical
знания/объекта, совместимость группы и разнообразие направления/медиа. Успех
не порождает «долг показать то же самое другим способом». Защита от повторов
проверяет предметное знание, объединяя прямое/обратное направление и алиасы.

## Проверка фактического задания и ограничение стоимости

После materialize сверить фактическое взаимодействие с выбранным. Если картинка
превратилась в текст, пересчитать разновидность; нельзя молча списать другой вес.
Проверить контракт, выбранную область и раскрытие ближайшего ожидающего знания.
При неуспехе убрать кандидата и попробовать следующего в ограниченном списке.
Пустая группа не даёт фиктивного долга и не вызывает бесконечную генерацию.

Индексы содержимого и capability-каталог кешировать по ревизии пакетов/настроек;
сроки и очередь не кешировать как содержание. История и статистика за один
проход, без запроса базы на каждого кандидата. Сохраняются бюджеты групповых
генераторов; новые механики не умножают полный перебор всех объектов на все форматы.
Окончательный лимит materialize закрепить сравнением с текущими счётчиками и
таймингами на одном устройстве. Не вводить произвольную очередь следующих задач:
каждый ответ может изменить доступность и раскрытия.

## Трассировка

На каждый выбор: категория работы и причина; наличие каждого семейства;
число предложений/нужных целей; причина отсутствия (не поддерживается, выключено,
мало совместимых целей, future, disclosed, cooldown, невалидно); компоненты
оценки/лимиты; несколько ближайших альтернатив; выбранный и фактический подтип;
дистанция знания/объекта; время и количество построений.

Сейчас checks.not-reached не отличает «формат не нужен» от «до ветки не дошли».
Новый отчёт должен показывать обе ситуации. Диагностика не меняет случайность,
порядок, зачёт или содержимое БД. Хранятся ограниченные ID/числа, не тексты ответов.

## Как проверять до внедрения

1. Зафиксировать исходный отчёт по текущему main. Отдельно считать реальные
   взаимодействия: match с одним объектом не выдавать за сопоставление.
2. Чистой моделью сравнить текущую политику, только штраф recall и общий выбор.
   Входы — одинаковые доступные семейства/знания/seed. Модель проверяет ритм,
   но не заменяет production trainer/контракты/IndexedDB.
3. Production-сценарии: 1/2/3/4/6/12/50 объектов; портреты; флаги; сущностные
   связи; две/несколько категорий; годы/числа; периоды; mixed богатый набор;
   несколько колод с людьми/событиями/книгами; ordering-only; отключённые поля.
4. Скорость 3/10/30 секунд; 30/100/300 экранов; seeds 1/17/41 плюс пакет seeds
   модели; правильные ответы, ошибки, раннее раскрытие, одни «вспомнил», перезапуск,
   полуночь, смена выбора колод. Все DB тестовые, личную базу не трогать.
5. Сравнивать первые 20 экранов и всю сессию. Счёт по экранам, действиям и
   активному времени: группа из 6 объектов — один экран, но 6 действий.

### Критерии принятия

- Богатый mixed при наличии альтернатив: опциональный recall не более 20% по
  окну выше; цель 10–15% на длинной сессии; отсутствие recall не компенсировать
  принудительными лишними повторами. Sparse/fallback отдельно в отчёте.
- Нет повторного успешного canonical вопроса через 1–2 экрана, когда есть
  другая допустимая работа; ошибки и единственная цель — явные исключения.
- При наличии нескольких взаимодействий нет серии более 3 одинаковых
  опциональных взаимодействий. Вариации текста choice это правило не обходят.
- Каждая поддерживаемая механика в специально подходящем сценарии достижима
  через реальный selector. Для непрерывно доступной опциональной механики на
  насыщенном наборе проверить ожидание до 30 выборов без срочных прерываний.
  Срочные прерывания и лимиты раскрытий не считать упущенной возможностью.
- Нельзя тестировать долю формата без записи, был ли он допустим; без дат
  отсутствие хронологии корректно. Постоянный cooldown/ранний return — ошибка.
- Сопоставление ≥3, конвейер 3–6, порядок 3–5; совместимость типов/групп, близость
  периодов и отсутствие незнакомых/внешних целей сохраняются.
- Прямые/обратные вопросы, изображения-ответы, обе числовые стратегии, обе
  границы периода и self-check покрыты отдельными достижимыми сценариями.
- Нет изменения FSRS от practice/подсказки/частичного знания; нет двойного
  зачёта и потери/сброса ошибки; подтверждение не раньше срока.
- Trace on/off даёт одну последовательность при одинаковом seed; повторное
  чтение/resume не меняет порядок. Старые backups/пакеты/настройки совместимы.
- Полный pnpm test, build и mobile smoke после продуктовой реализации; отдельный
  браузерный проход mixed со всеми новыми выбранными взаимодействиями.

## Порядок изменений после согласования

Сначала расширить диагностические сценарии и зафиксировать красные критерии
ритма/достижимости. Затем выделить классификацию фактического взаимодействия и
