# Текущее состояние Engi и следующий этап

Дата: 14 октября 2026. Основание: чтение текущего кода, последний полный прогон, проверки мобильных жестов и новый запуск `tests/feed-load-browser.mjs`. Обзор не означает проверку каждого экрана на настоящем iPhone.

## Что уже работает как система

- Знания описываются графом объектов и отдельных свойств. Основное изображение, флаг и год могут быть разными знаниями. Настройки обучения разделяются по типам объектов.
- Жизненный цикл первоначального обучения отделён от FSRS: первый вопрос, отложенное подтверждение, завершение обучения, дальнейшее повторение. Есть отдельный учёт ошибок и ограничение самостоятельного зачёта после подсказок.
- Групповые задания получают подходящие знания из очереди; сопоставление учитывает совместимость объектов и теги. Прямые, обратные, визуальные и хронологические представления используют общий слой контрактов и проверки результатов.
- Есть симуляции длительного обучения, диагностика выбора и времени операций, тесты повторных отправок и восстановления занятия.
- Пакеты импортируются семантически; удаление учитывает общих владельцев, личные зависимости и кэш файлов. Описания по ⓘ отделены от штрафующих подсказок.
- Последний полный прогон: 461 тест без ошибок. После него проверено исправление мобильного свайпа отдельными touch-тестами и сборкой.

Это основание для следующего этапа стабилизации. Само количество тестов не подтверждает отсутствие ошибок взаимодействия или интересность ленты для человека.

## Подтверждённые пробелы и риски

### 1. Мобильные проверки не входят в CI

`.github/workflows/deploy-pages.yml` запускает `pnpm test` и `pnpm build`. Браузерные сценарии выполняются отдельными командами; `pnpm test` включает только проверку обучения и `tests/*.test.ts`.

Последний дефект воспоминания был связан с отменой touch-жеста браузером и не мог быть найден этими логическими проверками. Нужен единый воспроизводимый smoke-набор: импорт → выбор колоды → новая карточка → первый вопрос → свайп воспоминания → исправление ошибки → восстановление занятия → изменение свойств → удаление пакета.

### 2. Текущий замер скорости не моделирует нормальную серию ответов

`tests/feed-load-browser.mjs` завершает знакомства, но вопросы проходит через `advanceFeed(session.id, true)`, то есть пропускает. Он проверяет отсутствие повторной компиляции на неизменённых данных, не стоимость реальных ответов и записи прогресса.

Новый замер на тестовой колоде штатов, локальная dev-сборка, CPU slowdown 4:

| Операция | Результат |
|---|---:|
| Перезагрузка и показ колод | 2117 мс |
| Нажатие «Начать обучение» → готовое задание, прогретый сценарий | 341 мс |
| Внутренний старт сессии | 186 мс |
| Внутренний переход между вопросами, медиана | 191 мс |
| Подтверждение новой карточки, медиана | 343 мс |
| Получение счётчиков, медиана | 137 мс |

Это диагностические значения, не гарантия скорости на телефоне. Следующий замер должен выполнять реальные правильные и неправильные ответы, закрывать ошибки, перезапускать приложение и охватывать несколько выбранных пакетов на production-сборке.

### 3. Границы кеширования и данных требуют упрощения

`selectNext` читает весь bundle и learningState. `getDayPlan` также читает данные и строит представление плана. В StudyFeed получение плана связано со сменами текущего задания. Ключи `compositionContext`, `canonicalTargets`, `goalProposalPool` и каталога используют сериализацию крупных структур; у pool в ключ включён массив enabled memories.

Это конкретные кандидаты для профилирования. По чтению кода нельзя утверждать, что каждый из них сейчас доминирует по времени.

Предлагаемая граница: неизменяемый индекс содержимого по ревизии импорта/настроек, отдельно состояние памяти и очереди. Результат перехода должен отдавать согласованные задание и счётчики; повторная загрузка всей структуры не должна быть обязательным шагом каждого ответа. Внедрять после замера, сохраняя проверку актуальности данных.

### 4. Несколько путей планирования увеличивают цену изменений

В `trainer-service.selectNext` есть lifecycle, endless, goal и legacy пути. Основной интерфейс запускает обучение с goals + endless и lifecycle по умолчанию. Старые ветки нужны для совместимости, тестов и существующих сессий.

Нужна явная граница между основным планировщиком и адаптерами совместимости. Без неё изменения расписания приходится проверять в нескольких реализациях. Удалять старые ветки можно только после инвентаризации потребителей и регрессий восстановления, не одним массовым рефакторингом.

### 5. Оформление вопросов ещё не полностью единообразно

В `session/composer.ts` обратный выбор изображения-свойства генерирует текст `Выберите … для: <название>`, хотя название уже показывается отдельно. Это конкретный оставшийся источник дубля, о котором пользователь ранее сообщал.

Потребуется единый контракт представления вопроса: что показано как подсказка, что написано в заголовке, где располагаются ⓘ и действия. Отдельные правки CSS и строк не заменяют такую проверку всех механик.

## Решение: следующий этап

**Первым сделать сквозную проверку реальной мобильной ленты и включить её в CI.** Сценарий должен использовать настоящие пакеты и настоящий trainer service, а не вручную вставленные готовые задания для всех проверок.

Критерии этого шага:

1. Правильные и неправильные ответы действительно записываются; счётчики проверяются как количества свойств.
2. Горизонтальный свайп с вертикальным отклонением, вертикальная прокрутка, отмена и мультитач проверяются touch-событиями.
3. Есть перезагрузка на новой карточке, после раскрытия ответа и посреди группового задания.
4. Проверяются изменение выбранных свойств и удаление пересекающихся пакетов.
5. Измеряются холодный запуск, ответ → следующий видимый вопрос и готовность изображения; отчёт показывает этапы и длительные блокировки основного потока.
6. Пороговые значения скорости задаются после нескольких воспроизводимых прогонов на одном окружении, с разделением холодного и прогретого сценария.

Далее — оптимизация подтверждённых узких мест, единое представление заданий и постепенная изоляция legacy-путей. Для интересности ленты добавить в отчёт распределение форматов, повторения одного объекта при наличии альтернатив, расстояние до подтверждения и долю повторов уже известных знаний. Эти метрики дополняют существующую трассировку и симуляции.

Новые механики и новые способы оценивать память пока не приоритет: следующий результат должен быть более предсказуемым, быстрым и проверяемым обучением с уже имеющимися форматами.
